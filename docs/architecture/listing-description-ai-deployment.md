# Architecture Decision & Deployment Model: AI-Generated Listing Descriptions

**Status:** Proposed (Milestone M38-04 Planning)  
**Author:** Mode 3 Orchestrator  
**Target Implementation:** M38-08  
**Scope:** Architecture & Deployment Specification Only (Zero Application/Persistence Code Changes)

---

## 1. Executive Summary & Recommended Architecture

The Udupi Property Explorer platform requires an engaging, responsive, and resilient drafting engine to assist brokers and dealers in authoring high-quality property listing descriptions. To achieve cost-effective production inference while maintaining strict factual grounding and non-blocking listing flows, we recommend a **self-hosted open-source model architecture** governed by a **Provider Abstraction Pattern**.

### Core Architectural Principles
1. **Never Block Listing Creation:** AI generation is strictly an asynchronous, optional enhancement. Listing persistence and form submission operate completely independently of drafting engine availability.
2. **Self-Hosted Primary Production Engine:** The primary drafting engine in production utilizes small, cost-effective open-source models hosted on rented server infrastructure (8–16 GB RAM profile).
3. **Deterministic & Grounded Guardrails:** The rule/template layer is not the main user-facing generator, but it is still required for fallback, prompt grounding, output validation, and resilience.
4. **Editable Draft Treatment:** LLM output must be treated as a draft and checked by deterministic validators before it is shown or saved. Brokers must explicitly review and save/publish the draft.
5. **Runtime Parity:** Development environments run the exact same model family and local runtime (e.g., Ollama or llama.cpp-compatible REST APIs) as production infrastructure.

## 2. Provider Abstraction (Backend Conceptual Pseudocode)

To decouple listing flow business logic from underlying inference runtimes and vendor APIs, all generation requests pass through a unified backend boundary service. Below is conceptual Java/Spring-style pseudocode illustrating the provider boundary:

```java
public interface ListingDescriptionProvider {
    ProviderName providerName();
    boolean isAvailable();
    ListingGenerationResult generate(ListingGenerationRequest request);
}

public enum ProviderName {
    NOOP, TEMPLATE, SELF_HOSTED_LLM, LOCAL_OLLAMA, OPENROUTER, REMOTE
}

public enum GenerationTone {
    FACTUAL, WARM, SHORTER
}

public enum GenerationStatus {
    SUCCESS, FALLBACK, FAILED
}

public record ListingGenerationRequest(
    UUID listingId,
    ConfirmedFactsPayload confirmedFacts,
    Locale locale,
    GenerationTone tone
) {}

public record ListingGenerationResult(
    GenerationStatus status,
    String description,
    ProviderName providerUsed,
    long generationLatencyMs
) {}
```

### Supported Provider Targets
1. **`SelfHostedLlmProvider`**: The authoritative primary production engine. Communicates via REST with a small open-weight model hosted directly on rented server instances (Ollama or llama.cpp server).
2. **`LocalOllamaProvider`**: Connects developer workstations to local open-weight instances running the same model family as production.
3. **`TemplateProvider`**: A zero-external-dependency deterministic string formatting engine. Acts as primary safety infrastructure and circuit-breaking fallback.
4. **`NoopProvider`**: Returns benign empty responses. Used during automated testing, CI pipelines, or when drafting features are globally disabled via flags.
5. **`OpenRouterProvider` / `RemoteProvider`**: Optional later adapters for external commercial APIs or free evaluation endpoints. Positioned strictly as non-blocking comparison/testing utilities, not required for MVP production.

## 3. First Production Mode

### Recommendation: `SelfHostedLlmProvider` as Primary, with `TemplateProvider` Fallback

For the first production release (M38-08), we recommend deploying the **`SelfHostedLlmProvider`** running small open-source weights as the primary user-facing drafting engine.

### Operational Profile & Guardrails
- **Normal Drafting Engine:** The AI model processes confirmed listing facts and produces fluent, natural real estate copy tailored to Udupi buyers.
- **Non-Blocking Guarantee:** If self-hosted CPU/GPU inference suffers from high load, spikes in latency, or instance reboot, requests abort cleanly and fall back to `TemplateProvider`.
- **Lowest Hallucination Risk for Templates:** While the LLM engine generates persuasive narrative copy, `TemplateProvider` provides the lowest hallucination risk for templates, because output is deterministic and limited to confirmed fields.
- **Strict Human Review:** Draft text generated by either provider is injected into form input controls. No background worker ever commits descriptions directly to database records.

## 4. Local Development Mode & Server Infrastructure Guidance

To maintain engineering discipline and zero cost overhead during local feature development, developers run lightweight instances locally matching production runtimes.

### Target Server Infrastructure Profile
Production and staging targets rented server instances constrained to standard RAM and disk footprints:
- **RAM Budget:** 8–16 GB RAM
- **Storage Budget:** 250–500 GB disk
- **Compute:** Rented cost-effective server instances (CPU-only acceptable initially if generation latency satisfies broker experience; GPU optional later).

### Realistic Small-Model Selection Matrix
Model selection must be rigorously tested against drafting copy quality, RAM pressure, inference latency, Kannada/English bilingual fluency, and broker usage concurrency.

**8 GB RAM Rented Server Profile:**
- `qwen3:4b`
- `gemma3:4b`
- `llama3.2:3b`

**16 GB RAM Rented Server Profile:**
- `qwen3:8b`
- `gemma3:12b` *(Deploy only if latency benchmarks and multi-tenant concurrency under broker usage are fully acceptable).*

**Strict Exclusions:**
- Avoid 30B+ parameter models on these server footprints.
- Avoid any deployment topology that mandates large, expensive multi-GPU memory clusters for MVP.
- Model weights (`.bin` / `.gguf`) are strictly excluded from repository source control.

## 6. Confirmed-Facts Payload & Sensitive Claims Guardrails

The rule/template layer is not the main user-facing generator, but it is still required for fallback, prompt grounding, output validation, and resilience. To eliminate prompt injection and factual fabrication, input to the generator is strictly restricted to verified backend fields.

### Tightened Sensitive Claims Policy
Do not casually include sensitive legal or marketing claims unless explicitly verified and stored as trusted backend fields. Sensitive claims include:
- `reraApproved` / RERA registration numbers
- `clear title` / legal document verification
- `approved layout` / municipal town planning approvals
- `high rental yield` / guaranteed investment returns
- `school proximity` / exact distance calculations
- `beach/sea/river view` / specific scenic sightlines

Only allowed when explicitly verified and stored as trusted backend fields.

### Sample Grounded Payload Schema
```json
{
  "propertyType": "AGRICULTURAL_LAND",
  "listingPurpose": "SALE",
  "landAreaAcres": 2.5,
  "locality": "Brahmavar",
  "city": "Udupi",
  "roadAccess": true,
  "waterSource": "BOREWELL",
  "currentCultivation": "COCONUT",
  "boundaryType": "FENCED",
  "askingPriceInr": 8500000,
  "negotiable": true
}
```
*(Notice: Unverified promotional claims and free-text broker comments are excluded).*

## 7. Safety, Privacy & Logging Rules

### PII Scrubbing
Before constructing the confirmed facts payload, deterministic pre-filters must scrub all personal identifiable information (PII), including broker contact numbers, owner identities, agency emails, and social handles.

### Tightened Observability & Logging Standards
To protect broker proprietary data and customer privacy, logging adheres to strict data minimization.

**Default Production Logging:**
- `listingId`
- `providerUsed`
- `latency`
- `status`
- `error category`
- `model name/version`
- `fallback used yes/no`

Do not log full prompts or full responses by default.

**Debug / Evaluation Logging:**
If debug/evaluation logging is enabled via configuration:
- It must be disabled by default.
- It must use redacted payloads (stripping potential PII).
- It should be restricted to non-production environments unless separately approved by security audit.

## 8. Timeout & Circuit-Breaking Cascades

System resilience relies on non-blocking HTTP timeouts and deterministic fallback cascades.

```text
[Broker Requests AI Description]
               │
               ▼
┌─────────────────────────────────┐       Success
│ SelfHostedLlmProvider (Primary) │──────────────────► [Inject Editable Draft into Form UX]
│ (qwen3:4b @ Rented Instance)    │
└─────────────────────────────────┘
               │
               │ Timeout (>8000ms), Instance Offline, or HTTP 5xx
               ▼
┌─────────────────────────────────┐       Success
│ TemplateProvider (Fallback)     │──────────────────► [Inject Deterministic Skeleton into UX]
│ (Deterministic Rule Engine)     │                    (Toast: "Generated via standard template")
└─────────────────────────────────┘
               │
               │ Unexpected Runtime Error
               ▼
┌─────────────────────────────────┐
│ NoopProvider (Safety Net)       │──────────────────► [Leave Description Input Unchanged]
└─────────────────────────────────┘
```

## 9. Implementation Sequence for M38-08

Milestone M38-08 implementation must execute strictly in these ordered phases:
- **Phase 1:** Provider abstraction + config + `NoopProvider`
- **Phase 2:** `ConfirmedFactsPayload` builder + blocked-claims validator
- **Phase 3:** `TemplateProvider` fallback
- **Phase 4:** `SelfHostedLlmProvider` against Ollama/llama.cpp-compatible API
- **Phase 5:** Frontend generate/regenerate/rewrite draft UX
- **Phase 6:** Observability, timeout, rate limit, rollout
- **Phase 7:** Optional OpenRouter/`RemoteProvider` later

---

## 10. Rejected Alternatives

1. **`TemplateProvider` as Autoritative Primary Mode:** Rejected because Udupi brokers require engaging, persuasive real estate narrative copy that deterministic string templates cannot provide.
2. **Enterprise Remote APIs (Vertex AI / OpenAI) as Mandatory MVP Dependency:** Rejected due to recurring per-token cloud costs and external vendor reliance. Positioned as optional later adapters.
3. **Client-Side In-Browser LLM Weights:** Rejected due to high mobile RAM requirements and cellular bandwidth caps common among field dealers.
4. **Unconstrained Free-Text Prompting:** Rejected due to prompt injection vulnerabilities and unverifiable amenity claims.
