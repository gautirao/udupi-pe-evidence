# E2E Supabase Auth Project Provisioning (#2236 Part B)

Durable documentation for issue #2236 Part B: a dedicated, disposable
Supabase project used ONLY for E2E authentication, so authenticated E2E
specs stop depending on the shared hosted production Supabase project.

**Status: Stage B-live is PENDING OWNER PROVISIONING.** The scripts below
are complete and tested against fake values (see "Verification" below), but
no real E2E Supabase project has been created yet. Until Part A (below) is
done by a project owner, `scripts/dev/verify-e2e-auth-project.sh`'s LIVE
steps will report `LIVE_VERIFICATION_PENDING_OWNER_PROVISIONING` and
`local-fixture-backend.sh` will keep running in `option1` (today's hosted
production Auth) mode.

## The secret-handling contract

This is the security-critical core of the whole design — read it before
running any of these scripts.

`.env.e2e.auth` (repo root, gitignored, mode 0600) holds exactly:

```
E2E_SUPABASE_PROJECT_REF=<ref>
E2E_SUPABASE_URL=https://<ref>.supabase.co
E2E_SUPABASE_ANON_KEY=<publishable key>
E2E_ADMIN_EMAIL= / E2E_ADMIN_PASSWORD=
E2E_BROKER_EMAIL= / E2E_BROKER_PASSWORD=
E2E_USER_EMAIL= / E2E_USER_PASSWORD=
E2E_DEALER_EMAIL= / E2E_DEALER_PASSWORD=
```

`E2E_SUPABASE_SERVICE_ROLE_KEY` is **never** part of that file. It is
supplied ONLY as an ephemeral environment variable for a single invocation
of `provision-e2e-auth-identities.sh`:

```
E2E_SUPABASE_SERVICE_ROLE_KEY=<value> \
E2E_SUPABASE_PROJECT_REF=<ref> \
E2E_SUPABASE_URL=https://<ref>.supabase.co \
E2E_SUPABASE_ANON_KEY=<publishable key> \
  ./scripts/dev/provision-e2e-auth-identities.sh
```

It is never written to any file, never committed, never logged, never
echoed, never added as a CI secret, and never passed to browser code.

> service-role key might be persisted alongside the other E2E project
> values. That was corrected during Stage B design review to match the
> contract above (B3) — this document, not the original issue text, is

## Why Option 2, and not Option 1 or Option 3

Three options were considered for how authenticated E2E specs get a valid
JWT:

- **Option 1 — keep using the shared hosted production Supabase project.**
  Rejected: it's a shared, externally-mutable dependency (anyone can change
  roles/users/rate limits on it at any time), so it's unfit as a
  deterministic merge gate. This is today's behaviour (`AUTH_MODE=option1`
  in `local-fixture-backend.sh`) and remains the fallback until Part A is
  done.
- **Option 3 — locally-mint a JWT (a test-only Spring profile /
  `application-e2e.yml` / conditional bean / test-only `JwtDecoder`).**
  **Explicitly rejected by the project owner.** This would add a
  JWT-validation relaxation path into a production-capable application —
  exactly the kind of security hole a determined attacker looks for. No
  Spring-side mechanism of this kind exists anywhere in this design; see
  `backend/src/main/resources/application.yml:46`, which already does a
  pure env substitution (`issuer-uri:
  https://${SUPABASE_PROJECT_REF}.supabase.co/auth/v1`, no default) and
  needs zero code change.
- **Option 2 — a second, dedicated, disposable Supabase project used only
  for E2E.** Chosen. `SUPABASE_PROJECT_REF` already fully parameterizes
  which project the backend validates JWTs against (Option 3's "whole
  backend mechanism" observation) — swapping which project both the browser
  and the backend point at is enough, with zero backend code changes.

## The 4 identities

Role vocabulary is fixed by `public.app_role` — there is **no** `owner`
role.

| var prefix   | email                          | role   |
|--------------|--------------------------------|--------|
| `E2E_ADMIN`  | `e2e-admin@udupi-e2e.invalid`  | admin  |
| `E2E_BROKER` | `e2e-broker@udupi-e2e.invalid` | broker |
| `E2E_USER`   | `e2e-user@udupi-e2e.invalid`   | user   |
| `E2E_DEALER` | `e2e-dealer@udupi-e2e.invalid` | dealer |

`.invalid` is a reserved TLD (RFC 2606) — no address in this table can ever
receive real mail, by design, regardless of what Supabase project they live
in.

Passwords are **generated by `provision-e2e-auth-identities.sh`** — they
are never caller-supplied, never derived from anything guessable, and are
distinct per identity (crypto-random, ≥32 characters).

## Part A — owner checklist (manual Supabase dashboard work)

These steps must be done by a project owner with Supabase dashboard access,
before Stage B-live can proceed. None of this repo's scripts can do them —
they require Supabase project creation and dashboard settings.

- **A1.** Create a new, dedicated Supabase project for E2E only (separate
  from production). Record its project ref, URL, and anon/publishable key.
- **A2.** Retrieve the project's service-role key. **Do not** put it in any
  file in this repo — it is used only as a one-shot env var for
  `provision-e2e-auth-identities.sh` (see the secret-handling contract
  above; the original issue text's A2 wording implying persistence was
  corrected).
- **A3.** Run `scripts/dev/provision-e2e-auth-identities.sh` (with the
  service-role key supplied ephemerally) to create the 4 identities and
  write `.env.e2e.auth`.
- **A4. Enable asymmetric (RSA/ECC) JWT signing keys.** A project still on
  legacy shared HS256 publishes an **empty** JWKS (`keys: []`) at
  `/auth/v1/.well-known/jwks.json`, and every authenticated backend request
  then 401s with no obvious cause — this is exactly what
  `verify-e2e-auth-project.sh` Step 4 checks for and explains. Rotate/enable
  asymmetric signing keys in the project's Auth settings before relying on
  this project for E2E.
- **A5. Raise the project's auth rate limit** (or otherwise ensure headroom)
  so a full E2E batch's password-grant logins don't collide with Supabase's
  default per-project rate limiting. `verify-e2e-auth-project.sh` Step 7
  checks this with 40 sequential logins and expects zero `429`s.
- **A6.** Confirm `E2E_SUPABASE_PROJECT_REF` is **not** equal to the
  production project's ref. Every script in this feature enforces this at
  runtime (fail-closed), but it's worth confirming by hand too.
- **A7.** Store the 4 identities' credentials as CI repository secrets when
  wiring PR-9's CI contract (see "CI contract preview" below). The
  service-role key is **not** part of this list (corrected from the
  original issue text — see the secret-handling contract above).

## Verification procedure (B9)

`scripts/dev/verify-e2e-auth-project.sh` is read-only and never writes any
file. It runs up to 7 steps, in this order (step 2 first, because it is
fail-closed and needs no network):

| # | Check | Live? |
|---|-------|-------|
| 1 | Project reachable / not paused (`/auth/v1/health`) | LIVE |
| 2 | Not production (collision check) | Runs first; works offline with fake values |
| 3 | OIDC discovery works, `issuer` matches exactly | LIVE |
| 4 | JWKS is asymmetric and non-empty (see A4) | LIVE |
| 5 | Each identity authenticates via password grant; token `iss` matches step 3 | LIVE |
| 6 | End-to-end: `local-fixture-backend.sh` in `option2` mode, one authenticated endpoint, assert 200 (401 = issuer/JWKS mismatch → re-check 3/4; 403 = role seed didn't land → different fix, see that script's Step F/F2) | **Never automated** — see caveat below |
| 7 | Rate-limit headroom: 40 sequential logins, assert zero 429s (see A5) | LIVE |

**Step 6 caveat:** unlike steps 1/3/4/5/7, step 6 is not a LIVE HTTP check
performed by this script. It is read-only by design and cannot launch
Docker/Spring Boot itself, so it **always** prints a `SKIP` with manual
instructions — regardless of whether `.env.e2e.auth` is present, and
regardless of exit code. A future CI wiring (PR-9) must not assume step 6
gates the pass/fail result of this script; it is a manual follow-up step
only.

Step 2 is also special: it only runs as a pass/fail check when there is
something to check — `.env.e2e.auth` present on disk, or the caller
explicitly exported `E2E_SUPABASE_PROJECT_REF`. In the true zero-config
case (neither — the normal state of a fresh checkout or CI run before Part
A is done), step 2 is reported as `SKIPPED` and does **not** count as a
failure; the script still exits `2` for the pending state below.

When `.env.e2e.auth` is **absent**, steps 1/3/4/5/6/7 each print a distinct
message containing the literal token
`LIVE_VERIFICATION_PENDING_OWNER_PROVISIONING` (step 6's SKIP message is
distinct from this pending token — see the caveat above).

Exit code contract (the three codes are mutually exclusive):

- `0` — all runnable steps passed
- `1` — step 2 ran and **failed** (`.env.e2e.auth` present but
  colliding/invalid, or `E2E_SUPABASE_PROJECT_REF` explicitly exported and
  colliding with production) — in this case the script **aborts
  immediately and refuses to run any LIVE step** (1/3/4/5/6/7); no network
  request is made against the flagged project. `1` is also returned when a
  LIVE step itself failed for a real reason (bad issuer, empty JWKS, 401,
  403, 429, etc.) with `.env.e2e.auth` present and step 2 passed.
- `2` — `.env.e2e.auth` absent and step 2 did **not** fail (it was
  `SKIPPED` in the zero-config case, or it `PASSED` against an
  explicitly-exported non-colliding ref) — LIVE steps are pending owner
  provisioning. This is the expected result on a fresh checkout / CI run
  before Part A is complete, and is what lets PR-9's CI distinguish
  "not provisioned yet, skip gracefully" (2) from "genuinely broken, block
  the PR" (1).

## B8 — rotation policy

- Re-run `provision-e2e-auth-identities.sh` to rotate all 4 identities'
  passwords at any time — it is idempotent (existing identities get a
  password/role update, not a duplicate-create failure).
- Rotate the service-role key itself via the Supabase dashboard as needed;
  since it's never persisted anywhere in this repo, rotating it requires no
  repo change — only supplying the new value the next time
  `provision-e2e-auth-identities.sh` is run.
- If the E2E project itself is ever suspected compromised or paused,
  recreate it from A1 rather than trying to recover it — it's disposable by
  design.

## CI contract preview (for PR-9 — not implemented here)

This section documents the intended shape for a **future** CI wiring PR; no
CI workflow is implemented by this change.

Repository secrets CI will need:

- `E2E_SUPABASE_PROJECT_REF`, `E2E_SUPABASE_URL`, `E2E_SUPABASE_ANON_KEY`
- `E2E_ADMIN_EMAIL` / `E2E_ADMIN_PASSWORD`
- `E2E_BROKER_EMAIL` / `E2E_BROKER_PASSWORD`
- `E2E_USER_EMAIL` / `E2E_USER_PASSWORD`
- `E2E_DEALER_EMAIL` / `E2E_DEALER_PASSWORD`

`E2E_SUPABASE_SERVICE_ROLE_KEY` is explicitly **not** a CI secret — CI
*consumes* the already-provisioned identities above; it never creates or
rotates them. Provisioning stays a manual, owner-run, one-shot operation
against a real Supabase dashboard.

Open questions for PR-9 to resolve (deliberately unresolved here):

1. **Fork-PR secret availability** — GitHub Actions withholds repository
   secrets from workflows triggered by a fork's pull request. E2E specs
   that need `.env.e2e.auth` may need to be skipped (not failed) on
   fork-originated PRs, or run only on a maintainer-triggered re-run.
2. **Free-tier pause vs. a required check** — a free-tier Supabase project
   pauses after a period of inactivity. If Step 1 (project reachability) is
   wired as a required CI check, an infrequently-run E2E project could start
   failing PRs for reasons unrelated to the PR's own changes. Needs a
   decision: keep the E2E project on a plan that doesn't auto-pause, add a
   scheduled keep-alive ping, or make the outage visibly distinct from a
   real regression.
3. **`storageState` reuse if rate-limited** — Playwright's `storageState`
   could cache a logged-in session across specs to reduce login volume
   against the E2E project's rate limit (see A5 / Step 7), but the existing
   local E2E harness doesn't currently do this. Whether to add it is a
   PR-9 decision, not a Part B one.
