### 3.1 A finding this run caught in its own artefacts, recorded rather than quietly fixed

The first sweep of this directory **FAILED**:

```
  shape-detector exemptions      : ['test_pii_filter.py']
  findings                       : 2
      [contact] test_adapter_99acres_commercial.py <raw text> -> '<10-digit shape>'
PII_RESIDUALS: FAIL
```

The cause was this lane's own test file: it planted a contact-shaped literal to prove the PII
gate detects one, and `pii_residuals.py` exempts exactly **one** file by name
(`test_pii_filter.py`). A new test file in a new directory is not covered by that exemption.

Two fixes were available. Adding this file to the exemption list was rejected: an exemption list
is how a fail-closed gate quietly stops being one, and the exempt file is precisely the place
where a real value would never be reported. Instead the planted number is now **constructed
digit-by-digit at runtime**, so the committed source contains no digit run at all while the
detector still receives a real contact shape to detect.

Both directions were then re-verified: the sweep reports 0 residuals, **and** the suite's
positive control still PASSES — the gate still detects the constructed value. A fix that had
silenced the detector instead of the literal would have shown up as that control flipping to
FAIL, which is why both were re-run rather than just the sweep.

The 2304-directory control sweep (PASS, 0 residuals) was run for the same reason: without it, a
clean result here could equally have meant the gate was broken.

The suite is built so that a severed detector fails it. Each gate is tested in both directions:
the office detector is asserted both to FLAG an office label carrying BUILDING **and** to stay
silent when the same label carries OFFICE, so it cannot be hardcoded to fail. The synthetic
control row is asserted to pass first — if it ever stops passing, every negative case below it
becomes meaningless, and the suite says so in that check's own name.

The office-precedence verdict on the real capture is **reported by the adapter, not asserted by
the suite**, so that PR #2594 merging cannot break these tests.

## 3.3 Promotion artefacts — VERIFIED against real Postgres

<!-- Heading corrected: an earlier revision read "written, not yet exercised against Postgres",
     which contradicted this section's own Status line below once the IT was run. A stale heading
     is what a skimming reader takes away, so it is fixed rather than left for the body to rebut. -->


`promote.sql` / `promote-rollback.sql` implement the explicit promotion step. Three decisions in
them are load-bearing:

- **Promotion writes `DRAFT`, never `LIVE`.** `SCRAPED` was rejected despite being V7's ingestion
  default: V60's RLS SELECT policy is `status='LIVE' OR (status='SCRAPED' AND is_valid=true)`, so a
  SCRAPED row is readable by any authenticated user unless `is_valid` is false — and using a
  data-quality flag to buy invisibility means a later reader "fixing the invalid rows" would
  silently publish them. `DRAFT` appears in no SELECT policy and in no Discover predicate.
- **`ON CONFLICT DO UPDATE`, not `DO NOTHING`.** The existing #2304 `import.sql` uses `DO NOTHING`
  throughout, so a rerun after a source correction silently no-ops while reporting success. That
  is precisely the failure mode #2575 names, so the promotion path must carry a change through.
  `status` is the one column deliberately excluded from the UPDATE, so a row already published by
  an explicit publish step is never silently demoted back to DRAFT.
- **The surrounding transaction is required, not stylistic.** V135's trigger is DEFERRED and fires
  at COMMIT. `promote.sql` writes the write model and the read model together, so it commits
  cleanly inside one transaction — and the identical statements run statement-autocommitted would
  NOT: the `property_listings` INSERT would commit alone and the guard would raise.

**Status: VERIFIED against real Postgres.** `CommercialImportPromotion2575IT` exercises both files
against a `postgis/postgis:15-3.4` Testcontainers instance with every Flyway migration applied.

```
$ mvn -f apps/api/pom.xml test -Dtest=CommercialImportPromotion2575IT \
      -DfailIfNoTests=true -Dsurefire.failIfNoSpecifiedTests=true
Tests run: 9, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS                                                          exit code: 0
```

Run **untagged and with no `-P`**, deliberately. The pom's surefire includes `**/*IT.java` and
excludes the `integration` group, so an untagged IT runs under a plain `mvn test`; each of the four
`-P` profiles instead sets surefire `<skip>true</skip>` and narrows failsafe to one named file, so
this IT under any profile would execute **nowhere** while the build still reported success.
`Skipped: 0` is part of the evidence, not decoration — `disabledWithoutDocker = true` turns an
absent Docker into a skip, and a skip is not a pass.

`Propagation.NOT_SUPPORTED` is also load-bearing: V135's trigger is DEFERRED and fires at COMMIT,
so under `@DataJpaTest`'s default rollback it would never fire and every negative case would pass
vacuously. These tests commit for real.

What the nine cover: promotion writes DRAFT never LIVE · a REJECTED candidate is never promoted ·
V102/V104 convergence · **the guard-has-teeth control** · idempotency · a source correction
UPDATES rather than no-ops · zero non-Commercial leakage with all five subtypes partitioning the
family exactly · sale/rent money separation · rollback restores clean state.

The guard control is the one that keeps the convergence test honest: without it, the convergence
assertion would pass identically against a database whose V135 trigger had been dropped or
mis-scoped — it would only prove `promote.sql` wrote two matching values, not that the schema
forbids the alternative. It asserts the unconverged write is actually **rejected**.

### A defect this IT caught, recorded rather than silently fixed

The first run reported **9 tests run, 8 errors, 0 skipped** — one root cause, not eight:

```
PSQLException: ERROR: type "public.property_type" does not exist
```

`promote.sql` cast `c.property_type::public.property_type`. That enum no longer exists: **V61**
converted `property_listings.property_type` to `VARCHAR(30)` and dropped the type, for the same
reason V60 did it for `status` — Hibernate binds these as VARCHAR and Postgres silently rejects
VARCHAR-vs-enum comparisons. The cast is removed and the column written as plain text.

Two things are worth noting about that first run. It is evidence the suite is **wired in**: 9 tests
executed and 0 were skipped, so this was a real failure rather than the "ran nowhere, reported
green" outcome the Maven profile hazard produces. And the single test that passed was
`v135GuardHasTeeth` — identified by enumerating the 8 named failures, not by subtracting counts —
which means V135's trigger was already demonstrably rejecting the unconverged write before the fix.
